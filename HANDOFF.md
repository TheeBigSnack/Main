## 2. The product rules (the short form; `CLAUDE.md` is authoritative)

Non-negotiables, enforced in code and by `test/posting.test.js`:

1. A person publishes every post and every edit. Lot Sync fills forms and opens pages; it never clicks Publish, Update, Delete or Mark as sold, and never posts or edits in the background. `extension/facebook/formMap.js` has no selector for those buttons; guard tests fail if any injected code gains a way to click or submit.
2. No detection evasion: no random "human" delays, no fingerprint/user-agent tricks, no proxies, no multiple accounts. Never ask for, read or store Facebook passwords, cookies or tokens.
3. Pre-owned only: `extension/src/classify.js` decides; new, demo, loaner and "needs a look" cars can't enter a posting flow; the side panel re-fetches and re-checks the car at post time.
4. Honest prices: the listed price equals the website price (dealer's chosen basis); price changes only mirror the website.
5. The dealership stays identifiable: every description names the dealership and the salesperson's role. First person is fine; posing as a private seller is not.
6. Facts only: descriptions state only facts in the source data; every number is checked against the source (`rewriteTemplate.js` `runGuardrails`).
7. Per-salesperson daily post cap (default 10), presented as a safety setting, never a guarantee.
8. No Meta/Facebook affiliation claims; "Facebook" and "Marketplace" only as plain names.

The one thing that runs on its own, only with the person's permission: re-reading the dealership website every 3 hours while Chrome is open to keep the to-do count current. It never touches Facebook then. Product copy, README and legal drafts say exactly that.

## 5. How the extension works (every flow, with the exact identifiers)

### 5.1 Storage (chrome.storage.local unless noted), all keyed per dealer website origin
- `settings:<origin>`: see `withDefaults` in `src/settings.js`: `{ version: 2, myStores[], basis: 'website'|'beforeFees', salesperson: {name, title}, dealer: {name, city, state, zip}, priceNote, dailyCap, rewrite: {enabled, endpoint, key}, defaults: {titleStatus, condition}, autoRescan, notify, rulesReadAt, legal: {version, acceptedAt}, readySort: 'newest'|'longest'|'price'|'name', newDays }` (`legal` since 0.5.0: the edition of the Terms and Privacy Policy accepted, `src/legalLinks.js` `LEGAL.version`, and when; both `''` until then, and nothing is recorded while `legalHosted()` is false; `readySort` and `newDays` (round K, `src/readyList.js`): the Ready to post list's order, set from its menu, and how many days a car counts as new, 1 to 30, default 7, from Settings' **Mark cars as new for N days**; both belong to the website and are not in the synced profile). Blank dealer city/state/zip are filled from the website's address at read time.
- `snapshot:<origin>`: `{ version: 1, site: {origin, host, name, title, address, adapter}, takenAt, complete, vehicles: { [vin]: snapshotEntry } }` where `snapshotEntry` has vin, name, stock, url, price, priceLabel, priceBeforeFees, status, statusLabel, availability, location, locationShort, photoCount, mileage, type, carfax, dateInStock (the website's own in-stock date as it gave it, or null), decision, reason, blockers[], and (round K) `firstSeenAt`: when Lot Sync first saw the car, carried over from the last saved snapshot, this scan's `takenAt` for a VIN that was not in it, null on a first scan and for entries saved before the field existed (`rescan.js firstSeenAt`; nothing is "new" by first sighting on a first scan). A car that left the list keeps the page it was last seen on in `missingPages` (below) and, when it had one, its sighting in `missingSeen` (`{ [vin]: firstSeenAt }`), so a car that comes straight back is not a first sighting: its `firstSeenAt` is what it was, or null, never this scan's time. `src/readyList.js` reads the two dates: the website's first, else the sighting, each with its source in the words shown.
- `diff:<origin>`: from `diffScans`: `{ firstScan, unreliable, warnings[], takeDown[], priceUpdates[], newArrivals[], becameReady[], needsALook[], takenAt, requests }`. Items carry `vin, name, stock, url, yours` plus `why/text/lastPrice` (takeDown), `from/to/change` (priceUpdates), `decision/reason/price/dateInStock/firstSeenAt` (newArrivals; the dates travel with the diff, which is saved even when the snapshot is not, so To do's date line never denies what the scan read). `unreliable` is set when a previous scan of 10+ cars lost more than half at once (`MASS_DISAPPEARANCE_SHARE = 0.5`): the popup, wizard and worker then keep the previous snapshot.
- `posted:<origin>`: `{ [vin]: { name, price, postedAt, listingUrl?, salesperson?, updatedAt? } }`. "Mark posted" (by hand) records no listingUrl; the panel's confirm-posted records the detected or pasted link.
- `boilerplate:<origin>`: lot-wide description sentences to strip.
- `postQueue:<origin>`: `{ vins[], index, status: 'running'|'paused'|'done', results: {vin: 'posted'|'draft'|'skipped'|'blocked'}, dealerTabId, windowId, startedAt }`.
- `drafts:<origin>`: cars saved as Facebook drafts during a queue.
- `postFlow:<origin>`: the side panel's in-progress post (FLOW_FIELDS) so the panel can be closed and reopened.
- `wizard:<origin>`: the wizard's persisted state (`active`, `step`, answers); `wizardDone:<origin>`: ISO string when finished, or `{skipped: true, at}` when the popup's "Not now" was clicked.
- `pilot:<origin>` (0.4.0): `{ version: 1, posts: [{ vin, name, salesperson, queue, startedAt, reviewedAt?, formOpenedAt?, filledAt?, endedAt?, outcome?, seconds?, reason? }], fills: [{ at, vin, mapVersion, filled[], partial[], blocked[], changed[], preexisting }], flags: [{ vin, kind: 'takeDown'|'price', name, why?|from?/to?, flaggedAt, doneAt?, how?: 'detected'|'manual'|'cleared', hours? }] }`; see `src/pilot.js` and `PILOT.md`. Cleared by the Numbers tab (**Clear the numbers**) or "Clear everything for this website"; pruned on every record to the newest 500 entries per list and nothing older than 90 days (`MAX_ENTRIES`, `PILOT_RETENTION_DAYS`), open flags excepted.
- `sync:<origin>` (0.5.0): the per-website sync state for the accounts (`src/sync.js` `nextSyncState`: `{ since, dealershipId, role, plan: { state: 'none'|'pilot'|'active'|'lapsed', pilotEndsAt, currentPeriodEnd, seats }, postsToday: { count, from, to } | null }`; a 402 from the function stores the plan and nothing else), written by `syncOnce` (`src/accountFlow.js`) from the worker after each rescan, from the side panel's confirm-posted (`syncNow`, fire-and-forget) and from Settings' Sync now; cleared by Sign out so the next sign-in starts with a first sync.
- `account` (global, 0.5.0): the signed-in session (`src/account.js`: `{ accessToken, refreshToken, tokenType, expiresAt, user: { id, email }, signedInAt }`), local storage only, never the sync area. Every key name comes from `src/storageKeys.js` (`siteKeys(origin)`, `GLOBAL_KEYS`); `test/storageKeys.test.js` fails on a key spelled anywhere else.
- `sites` (one object for all origins): `{ [origin]: { name, adapter, service: {search, apiKey, visibleStatusValues, hasHelper}, site, auto, lastScan, lastAttempt, lastError, lastReason, lastNotifiedCount, lastSyncAttempt?, lastSync?, lastSyncError? } }`. The service worker rescans entries with `auto: true`.
- Requests from popup to panel: `postRequest`, `setupRequest`, `upkeepRequest` (each `{ origin, dealerTabId, windowId, at, ... }`), plus `lastPostOrigin`.
- `devOverrides`: test-only overrides merged over `FORM_MAP` (createUrl, listingUrlPattern, yourListingsUrl, settleMs, recheckMs, ...).
- chrome.storage.sync `profile`: the salesperson's profile (`profileFrom`: salesperson, dealer, myStores, basis, priceNote, dailyCap, defaults, rewrite without the key, legal, savedAt), which records the `origin` it was saved on (0.4.0). `settingsFromProfile` seeds a website that has no settings yet: the whole profile when the origins match (or the profile predates `origin`); on any other website only the person's part (salesperson, defaults, legal, the rewrite endpoint with the key blanked) carries over and the website fills the dealership fields. ### 5.3 Scan (popup "Scan website", the wizard, and the worker)
`performScan({ tabId, origin, settings, settingsFromProfile, snapshot, posted, boilerplate })` in `src/scanRunner.js`: `probeTab(tabId)` injects the neutral `probeSiteInPage` (MAIN world: the site name and the schema.org address), then each adapter's `probeInPage` in `ADAPTERS` order until one answers with its service (`{ site, service, adapterId }`); `detectAdapter(probe)` (none: `UNSUPPORTED_MESSAGE`, which lists every adapter's name); `search = searchViaTab(tabId, adapter, service)` (each request is made inside the dealer tab by the adapter's `searchInPage`); `scanWithSearch({ adapter, search, site, settings, prevSnapshot, posted, options: adapter.scanOptions(service), boilerplate })` runs `adapter.scan(search, { ...options, confirmVins, confirmUrls, lastSeen, postedVins })`, normalizes, settles the store labels over the lot (`shortLocation`), assesses (`assessVehicle`), builds the snapshot, `diffScans`, and the boilerplate; on a first scan or profile-seeded settings it settles the store choice (`defaultStores`) and re-assesses; then `rememberSite(origin, {...})` records the adapter, the service and `photoOrigins` for background rescans. The popup, the wizard and the worker keep the previous snapshot when `diff.unreliable`. The worker's `runRescan` calls the same `scanWithSearch` with `adapter.makeDirectSearch(service)`.

What carries from one scan to the next (`scanWithSearch`, `snapshotOf`): each car's `firstSeenAt` (from the last saved snapshot, `rescan.js firstSeenAt`; a scan whose snapshot is not saved changes no dates, since the next scan carries from the saved one again), `confirmVins` (the last snapshot's VINs and the posted ones), `confirmUrls` (each car's `url` from the last snapshot, plus its `missingPages`: the last page of every such car that was not in that scan, so a posted car that left the list on a bad server day can still be checked at its page) with each such car's `firstSeenAt` in `missingSeen`, `lastSeen` (the last snapshot's entries) and `postedVins`. A scan result's optional `unread` (cars the website still lists whose details could not be read this time) keeps those cars' entries from the last snapshot unchanged. A `descriptionRaw` of `null` (a car not re-read) keeps the saved boilerplate lines next to the ones found now. An incomplete scan puts `incompleteWarning(res)` first on the to-do list.

`adapters/dealerInspire.js` `scan(search, { status, vins, confirmVins, fullRecords })`: POSTs `{ type: ['Used','Certified Used'], perPage: 200, page, sort..., filters }` (fields listed in `FIELDS`), walks pages, retries in other sort orders when paging is unstable, de-duplicates by VIN, then looks up VINs from the previous snapshot that the paged search missed (`confirmVins`, batches of 50) so a car is only called "gone" when a direct lookup fails too (`confirm: { checked, notFound, error }`). `getDetails(search, vin)` fetches one full record (all photos, description, features) for post time. `makeDirectSearch(service)` is the same POST from the worker (verified live: the Cars Commerce service answers direct requests from outside the page with HTTP 200). Its probe reads `window.SEARCH_SERVICE` (`search` URL, `apiKey`, `visibleStatusValues`) and searches through the page's own `IDPSearchServiceHelper.getListings` or a fetch with `x-api-key`.

`adapters/schemaOrg.js` (last in `ADAPTERS`) reads any website that publishes schema.org vehicle markup, through the shared readers `schemaOrgParse.js` (`parseVehiclePage(html, pageUrl)` → `{ vehicles, facts }`; pure, string-level) and `schemaOrgNormalize.js` (`normalizeVehicle(node, { url, facts })`; a price only when it is one US-dollar offer the page's visible text also shows as its current price, never crossed out or after Was/MSRP; no `priceCurrency` counts as dollars only when the page shows the amount with a dollar sign). `probeInPage` answers on a list of cars or one car's page, never on Facebook (`{ kind: 'schemaOrg', origin, listUrl }`); `search({ url })` is one same-origin GET (`searchInPage` in the tab, `makeDirectSearch` without cookies from the worker). `scan` walks `listUrl` and its rel=next pages, the robots.txt sitemap filtered to this lot's own car-address shape when the list shows fewer cars than its count, then each car's page two at a time (`CONCURRENCY`, no pauses); a 403, 429, 503 or bot check stops it, and so do three car pages in a row that fail (`MAX_FAILED_IN_A_ROW`). At most `MAX_CAR_PAGES` car pages a scan: posted cars first, then the oldest `pageReadAt`. Later scans read only new, posted, unpriced or changed cars (`lastSeen`, `postedVins`); a car whose page fails keeps its last reading (`unread`), or on a first read takes the list's data. A missing car is checked at its last page (`confirmUrls`): gone only on 404/410 or SoldOut, or (once the site's car pages are known to carry their own VIN) a redirect away or the site's own data without it; anything else sets `confirm.error` and nothing is marked gone. `getDetails(search, vin, { url })` reads the car's page first. Tested only on synthetic pages (`test/fixtures/structured/`, `test/helpers.js standardSite`, `test/e2e/mock-standard-site.mjs`, the sandbox's second sample); no platform is claimed.

### 5.4 The pre-owned gate (`src/classify.js`)
Three signs from the website are compared: inventory type ("Used"/"Certified Used"/"New", or a schema.org itemCondition value such as https://schema.org/UsedCondition), the condition word in the vehicle page URL, and the condition word at the start of the title. Demo/loaner flags always win (sold as new). A car the website lists as damaged or refurbished (the words, or schema.org's DamagedCondition/RefurbishedCondition) goes to review ("The website lists it as damaged (inventory type). Check its condition before posting."); a new car stays new. One sign alone, a schema.org value included, still needs a second sign or a Carfax link. A Carfax link supports pre-owned but its absence never blocks. Mileage never makes a car "used" (the live site has "New" units with thousands of miles). Disagreement or oddity -> `review` ("Needs a look"). A trailer, RV, powersport vehicle or boat (`notACar`, from `listingData.js`'s `readVehicleKind`: the body style's words, where a car body style such as "Crew Cab Pickup - Trailer Tow" always wins; only with no body words, a make that builds only that kind, matched on `makeKey`, which drops punctuation and company words so "Thor Motor Coach, Inc." is "thor" and "Can-Am" is "can am", as the whole make or its first words) goes to `review` with the reason in the website's words, and `recheck` says the same at post time; a new one is still skipped. `FORM_KINDS` (car/truck, motorcycle) are the only vehicle types the form is filled in for. Ready check: photos, a price, on the lot, not sale-pending, at one of `myStores`. Blocker codes: `no-photos`, `no-price`, `sale-pending`, `not-on-lot`, `other-store`.

### 5.7 First-run wizard (`wizard.js` and `src/wizardSteps.js`, steps `welcome, scan, store, you, account, address, price, permission, rules, terms, done`; `account` only when `accountsConfigured()`)

### 5.8 Automatic rescans (`background.js`, `rescanSchedule.js`)
`chrome.alarms` `lot-sync-rescan`, period 180 minutes, created on install/startup and by `ensureAlarm`. On alarm: for each `sites[origin]` with `auto`, if `isDue(latestOf(lastAttempt, lastScan))` (period minus 5 minutes slack), `runRescan(origin, { reason: 'alarm' })`: requires the entry's service, an adapter, `chrome.permissions.contains` for the origins, and existing `settings:<origin>` (never invents defaults, never writes settings); `scanWithSearch` with `adapter.makeDirectSearch(service)`; saves diff and boilerplate (snapshot only when not unreliable); `updateBadge` (sum of `todoCountFor(diff)` over all sites: the person's own take-downs, price updates and needs-a-look items); a desktop notification (`chrome.notifications.create`, icon `icons/icon128.png`) when the count rose above the person's outstanding list (`todoCountFor(previous diff)`), `settings.notify !== false`, and the reason is the alarm. Failures are recorded as `lastAttempt`/`lastError` and the popup shows them on To do (`#scheduleWarning`), including "no permission" with an "Allow automatic rescans" button. Settings also has that button; ticking the rescan box asks Chrome from the Save click and stays off if refused.

### 5.9 Listing upkeep (`upkeep.js`)
Popup To do: "Open listing" (take-down) or "Open & update price" (`data-action="upkeep"`, `data-kind`), which writes `upkeepRequest` (`kind: 'takeDown'|'price'`, price, listingUrl, name, listedPrice). The panel opens the saved listing link (or `FORM_MAP.yourListingsUrl` with a note when none was saved) in a new tab and polls it every 1.5 s with `readListingInPage(map, LISTING_SIGNS, { id, name })`, which returns `{ url, title, prices[], sold, unavailable, matchesId, matchesName, hasPriceBox, priceBoxValue }` from the page's static text (buttons, links, menus, tabs and dialogs skipped; the sold sign only in chunks of 40 characters or less). Nothing happens unless `matchesId || matchesName` (the listing id in the address, or the car's year/make/model in the title/text); otherwise the panel says which listing to open. Price: when this car's edit form shows a Price box, `fillPriceInPage(map, price)` sets it (up to 4 times if the loading form overwrites it) and reads it back; when the box is gone and the page shows the new price, the item is finished (`markPriceUpdated`, dropped from `diff.priceUpdates`). Take-down: finished when sold/unavailable flips from false on the first read of that page to true (`markTakenDown`, dropped from takeDown/priceUpdates/needsALook). "I updated it" / "I took it down" finish by hand; "Not now" cancels. The panel refuses an upkeep request while a post is under way (steps checking/review/filling/probe/publish) and stops a waiting upkeep when a post or the wizard starts. Each panel instance acts only on requests for its own window and ignores requests older than 10 minutes.

### 5.10 Descriptions
`description.js`: the site's `description` field mixes a lot-wide disclaimer, raw equipment dumps and sometimes a real write-up; `findBoilerplate` finds sentences on 30%+ of the lot and on at least 3 cars (`MIN_BOILERPLATE_COUNT`, so a 2- or 3-car lot keeps its write-ups); `cleanDescription` strips them plus bullets, award lines and comma dumps. `rewriteTemplate.js` `buildTemplateDescription` writes 60–120 words in first person with 4–6 features (priority list), the price note, the sign-off "I'm [name], [role] at [dealer]", and a VIN line (`ensureVinLine`). `runGuardrails` checks: every number in the text is in the source (vehicle, dealer, price note, price), no banned phrases, dealer named, length, no shouting, "one owner" only with the Carfax flag. `rewriter.js` asks the backend when Settings enables it, regenerates once on a failed check, then falls back to the template.

## 6. What the live Facebook form taught us (six live runs on 2026-09-27; all handled in `fillForm.js`)
1. Dropdowns are slow, custom comboboxes that open one at a time; the option list is drawn late. The fill waits up to 6 s per popup, scopes the option search to the open popup, and retries a dropdown on the spot when its read-back disagrees.
2. Price and mileage are reformatted by the form (commas); the read-back accepts digit-equal values.
3. Location suggestions include same-named towns in other states ("Waynesburg, Ohio"); the fill picks the suggestion matching the dealer's state (`locationExpect`), types the ZIP when known, and the state comes from the site's address. Sending Escape to the location box clears it: Escape is only ever sent to `document.body`.
4. **Facebook restores a saved draft ("2020 Honda Accord EX-L") a few seconds after the create page opens, over whatever was filled.** The fill waits until the identity fields have been still for 2 s (up to 6), fills the VIN first, re-checks every field after `recheckMs` (3 s) and re-applies anything changed underneath, and the panel names what Facebook changed and asks the person to delete that draft (Your listings -> Drafts). The owner's stale draft may still exist; ask them to delete it.
5. Make and Model are typeaheads that show default suggestions (Honda, then Accord) and **commit the first suggestion on blur**. They are typed one key at a time, only a suggestion containing the typed text is picked, the box is closed with Escape (never blurred). Make may be a dropdown-style control on some loads.
6. The clean-title control is a checkbox labelled by nearby text; the photo limit text reads "up to 20 photos"; the read-back of a box that empties itself after a pick uses the visible text beside it.
7. After these fixes, single cars and a queue ran with nothing under "Couldn't fill" (`formMap.js` `verifiedAgainstFacebook: 'live runs 2026-09-27, all fields'`).

Not yet verified on the live site: `yourListingsUrl` (`/marketplace/you/selling`), the listing page's sold/removed wording (`listingSigns.js`), the edit page's URL shape (the code accepts the listing id anywhere in the URL, or the car's name on the page) and its Price box; the wizard's permission prompt; a real alarm rescan and notification.
