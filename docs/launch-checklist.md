# Launch checklist: from the end of the pilot to the first paying dealers

Everything between the pilot's last week and the first invoice, grouped by who does it. Each item has a "done when" so nobody argues about whether it is finished. No dates: the order is the plan, and the milestones in `PLAN.md` say roughly when. The rules in `CLAUDE.md` apply to every item.

The pilot itself ends when `PILOT.md`'s three criteria are met and the manager has confirmed the numbers. This list starts there.

## Legal

- [ ] **Attorney answers received**, at least on sections 1 (Meta's Terms and how to describe the risk), 2 (the founder's employment at the pilot dealer) and 4 (advertising law and the price note) of `legal/questions-for-attorney.md`. Done when: each answer is filed next to its question and the product copy, the posting rules and the marketing wording say what the attorney said we may say.
- [ ] **Terms of Service and Privacy Policy final.** Done when: `legal/terms-of-service.md` and `legal/privacy-policy.md` carry the attorney's changes and no "DRAFT" line, `legal/legal-status.json` says `"draft": false` and `npm run legal-pages` has rewritten `site/legal/` (it refuses while a text keeps its DRAFT line or a [bracket]; the titles lose their "(draft)"), the Pages workflow has deployed `site/` (`docs/website.md`), and `extension/src/legalLinks.js` has the pages' addresses (`https://<the site's host>/legal/terms/`, `/legal/privacy/`, `/legal/posting-rules/`, the host being `siteUrl` in `site/config.js`) and a new `version` so every salesperson accepts the final texts.
- [ ] **Posting rules final.** Done when: `legal/posting-rules.md` has the attorney's wording and `test/postingRules.test.js` still passes (the wizard shows the same text).
- [ ] **Dealer Subscription Agreement and Schedule A ready to sign.** Done when: every bracket is either filled or is a field the dealer fills, the attorney has read section 2 (the dealer's authorisation to read its website) and the liability split for wrong prices, and Schedule A is blank of any pilot value.
- [ ] **Entity formed.** Done when: the entity named in the Terms, the Privacy Policy and the agreements exists, and "[Lot Current entity name]" appears in no legal document.
- [ ] **Insurance in place.** Done when: technology errors and omissions and cyber liability policies are bound at the limits the attorney thought sensible for this stage, and the certificate is where a dealer can be shown it.
- [ ] **Trademark question answered.** Done when: the attorney has said whether "Lot Current" is clear to use and whether to file, and that decision is recorded in `legal/trademark-note.md`.
- [ ] **Sales tax question answered.** Done when: the attorney has said what to collect on subscriptions in the state we sell from, and Stripe is set up to do it.

## Accounts and billing

- [ ] **Supabase project live** (`PLAN.md` M4). Done when: magic-link sign-in works for two people at one dealership, row-level security tests show one dealership cannot read another's rows, and the rewrite endpoint refuses unauthenticated calls and stops at the monthly cap. `npm run check-deploy` passes with `LOTSYNC_TEST_TOKEN` set (`supabase/README.md` step 6): no line reads FAIL; the billing and lead lines may read note ("not deployed yet") until the Stripe and landing-page items below.
- [ ] **The manager view hosted at its own address** (`docs/production-setup.md`, step 6). Done when: `manager/config.js` names the production project (`npm run set-project -- --check` passes), the Manager view workflow has deployed it, the address answers over HTTPS with the headers in `manager/_headers`, and the project's Site URL and Redirect URL are that address, so a manager's sign-in link lands back on it.
- [ ] **Paste the sign-in email templates into the hosted project.** Supabase's own sign-in emails carry only the link, so without these a salesperson gets no code to type into the extension. In the Dashboard, Authentication, Email Templates, paste `supabase/templates/magic_link.html` into **Magic link or OTP** with the subject "Your Lot Current sign-in code", and `supabase/templates/confirmation.html` into **Confirm sign up** with the subject "Your Lot Current sign-in code" (older Dashboards call them Magic Link and Confirm signup). The first goes out for every sign-in while "Confirm email" is off; the second only while it is on, which is how a new hosted project starts, to an address signing in for the first time. Under Authentication, Sign In / Providers, Email, check that the email OTP length is 6 digits and the email OTP expiration is 3600 seconds: the extension's code box takes six digits and the emails say the code works for one hour (`supabase/README.md`, "Sign-in emails"). Done when: a new test address has signed in twice, once with the code in the extension and once with the link in the manager view, and each email had that subject, the code, the link and nothing of Supabase's default wording.
- [ ] **Choose the sender.** Supabase's built-in sender is for testing only: it delivers only to the addresses of the project's own team, and only a few emails an hour (its docs say 2, and that the number can change without notice), so a salesperson would get no code. A product that dealers pay for needs the owner's own SMTP provider, which is a paid service and the owner's decision (`CLAUDE.md`: ask before adding one); nothing in the repo picks one. The setting (Dashboard, Authentication, Emails, SMTP Settings) needs the provider's host, port, user and password, a sender address on a domain the owner controls, and a sender name ("Lot Current"). Add the SPF and DKIM records the provider gives for that domain, and turn off the provider's link and open tracking: the templates carry no tracking, and Supabase's docs warn that tracking rewrites the sign-in link so it no longer works. Supabase starts a custom sender at 30 emails an hour, the limit `supabase/README.md` step 3 asks for. Done when: the settings are saved and a sign-in email sent to a test address at each of two different mail services arrives in the inbox, not marked as spam, with a code the extension accepts.
- [ ] **The posted registry syncs.** Done when: two salespeople on two machines see the same posted registry, and a car posted on one shows on the other after its next scan.
- [ ] **The manager view works** (`manager/`). Done when: a manager at the pilot dealer signs in and sees posts per salesperson, sold cars still listed and for how long, and price mismatches, with the numbers matching the salespeople's Numbers tabs for the same week.
- [ ] **Stripe set up** (`PLAN.md` M5). Done when: a per-rooftop subscription with the free pilot period and the customer portal exist, a test-mode dealer can subscribe, start the pilot period and manage billing without help, the prices are the ones in `marketing/pricing.json`, and `npm run check-deploy` shows all three billing lines as ok, the webhook's included (none a note).
- [ ] **Pricing confirmed.** Done when: a dealer has agreed to pay a price in writing, `marketing/pricing.json` has `"hypothesis": false` and the same numbers, and `test/marketing.test.js` still passes.
- [ ] **The per-salesperson cap follows the account, not the browser** (`PLAN.md`, "Wider use", M4). Done when: the same person on two machines shares one day's count.
- [ ] **Retention runs.** Done when: the retention list (`supabase/README.md`, "The retention line") is run once a week, by a named person, from a recurring calendar entry; a dealership's records are deleted within the 30 days the agreements promise after a subscription or pilot ends; and the deletion was tried once on a test dealership.

## Sales

- [ ] **Positioning confirmed by the pilot numbers.** Done when: `marketing/positioning.md` says which of its hypotheses the pilot supported and which it did not, with the numbers from the manager-confirmed CSVs, and nothing in it is still labelled a guess that the pilot could have settled.
- [ ] **The sales sheet carries only permitted numbers.** Done when: every number in `marketing/sales-sheet.md` comes from the pilot CSVs, the manager has confirmed it, the store has given written permission under pilot agreement section 3 (or the store is not named), and `test/marketing.test.js` passes.
- [ ] **Demo script rehearsed.** Done when: the 10-minute demo in `marketing/demo-script.md` has been run end to end twice on a dealership website that is not the pilot's, without publishing, and the "If something goes wrong" section covers everything that went wrong in rehearsal.
- [ ] **The pilot offer and onboarding emails updated.** Done when: `marketing/pilot-offer-email.md` and `marketing/onboarding-emails.md` describe the store install and the accounts, and every bracket is a field the sender fills.
- [ ] **The website on GitHub Pages** (`site/`, `.github/workflows/pages.yml`, `docs/website.md`). Done when: the repository's Settings, Pages has Source set to GitHub Actions, the Pages workflow has run green from the default branch (it deploys from whatever branch is the default, and skips every other branch), and every page of the site map answers at `https://lotcurrent.com/` with its own title, nothing in the browser console and no failed request (the same things `npm run test:site` checks locally). Already done: Source, custom domain, verification and Enforce HTTPS are done; the first deploy happens when the website pull request is merged into the default branch.
- [ ] **The domain and `siteUrl`.** Already done: `lotcurrent.com` is bought, its DNS points at Pages (apex and `www`), it is verified, HTTPS is enforced, and `siteUrl` is set with the outputs committed; what is left is the deploy and the live check. Done when: the owner has bought the domain, pointed it at GitHub Pages with the DNS records GitHub's own documentation gives (linked from `docs/website.md`; nothing in this repo guesses them), added it under Settings, Pages, Custom domain, verified it and ticked Enforce HTTPS; `site/config.js` has `siteUrl` (the https origin, no path, no trailing slash); `npm run site-pages` and `npm run legal-pages` have been run and their outputs committed, `sitemap.xml` and `CNAME` among them; `node scripts/site-pages.mjs --check` no longer reports "siteUrl is not set: the site is not ready to publish" (until then that line is the reported condition this item clears, and `npm test` stays green either way); the Pages workflow has deployed; `https://<domain>/` answers over HTTPS with every canonical, `og:url` and sitemap address on that domain; and `npm run test:site` passes against the committed files.
- [ ] **The demo request form open.** The form is on the home page in every state, but says "The demo request form is not open yet" and sends nothing until one of two values in `site/config.js` is set: `demoEndpoint` (the `lead` function's address; set its `LEAD_ORIGINS` secret to `siteUrl`) or `demoMailto` (`mailto:` plus a real inbox; a reserved placeholder domain is refused by the tests). Done when: one of them is set, `npm run site-pages` has been run and committed, a request sent from the live page lands in `demo_requests` (for the function, `LOTSYNC_SITE_ORIGIN=<siteUrl> npm run check-deploy` shows both lead lines as ok) or in the inbox, and a named person reads that inbox or table each business day.
- [ ] **The business details for the website's structured data** (optional). The home page's structured data carries an Organization record until `site/config.js` `business` is filled; with the required fields (`name`, `streetAddress`, `addressLocality`, `addressRegion`, `postalCode`, `addressCountry`) it carries a LocalBusiness record instead, and the generator refuses a half-filled one. Done when: either the fields are left empty on purpose, or every required field holds the entity's real registered address (the entity from the Legal group above, never a dealer's), the optional ones (`legalName`, `telephone`, `email`, `url`, `openingHours`, `areaServed`) hold only what is true, `npm run site-pages` has been run and committed, and the owner has checked the record on the live home page's source.
- [ ] **A pipeline sheet exists.** Done when: demos, pilots and paid dealers are tracked in one place with the source of each (in-person demo, forum, LinkedIn, association event), as `PLAN.md`'s launch plan asks.

## Design partners

- [ ] **Three to five dealers agreed** (`PLAN.md` M6). Done when: each has signed the pilot agreement or the subscription agreement, named its manager and at least two salespeople, and its website has been scanned once by the owner to confirm the platform is one Lot Current reads.
- [ ] **Sister stores first.** Done when: the pilot dealer's sister stores under the same group website have been offered the pilot before any outside dealer, and their answer is recorded in the pipeline sheet.
- [ ] **Each partner is active.** Done when: each partner dealer has at least two salespeople posting and one manager using the manager view, as M6's first criterion asks. In the usage report (next item) that is a row with `active_salespeople` of 2 or more and `managers` of 1 or more, plus the manager's word that they use the manager view. `active_salespeople` counts the people who belong to the dealership as salespeople and posted at least one listing in the report's 7 days; a manager who posts is counted in `posts`, not there, and so is someone who has left. The database records nothing when a manager opens the manager view, so `managers` only says someone holds the role: ask at the weekly check-in.
- [ ] **Run usage_report weekly and keep the partner list.** Done when: `select * from public.usage_report();` is run once a week in the Dashboard's SQL editor, by a named person, from a recurring calendar entry (`supabase/README.md`, "Usage report"); each partner's row goes into the pipeline sheet under that week, with its `plan_state`, `managers`, `salespeople`, `active_salespeople`, `posts`, `cars_listed_now`, `open_take_downs`, `open_price_changes`, `oldest_open_hours` and `last_synced_scan_at`; and that list, as the weeks recorded it, is the partner list with usage numbers the M6 demo shows.
- [ ] **Each partner has done the set-up.** Done when: every salesperson has finished set-up, including the posting rules and the Terms, and has run one dry run (**Open the form and check fields only (nothing filled)**) with nothing under "Not found".
- [ ] **The next platform's first dealer is among them, or is named.** Done when: `docs/next-platform.md`'s output line is filled in with a dealer who has agreed to be the first on that platform.
- [ ] **A weekly check-in with each partner.** Done when: the check-in is in the calendar, the Numbers tab (or the manager view) numbers are collected each week, and the log and the pipeline sheet are updated from it.

## The line that says we are launched

Every item above is ticked, at least one dealer outside the pilot is paying through Stripe, and its salespeople post from the Web Store build with support answering within one business day.
