# Dealer-website adapters

Every platform Lot Current reads lives here, one file per platform (plus a normaliser file next to it when that reads better), behind one contract. `index.js` lists the built adapters in `ADAPTERS`, in the order their in-page probes are tried. Nothing outside this folder knows a platform's name, its service, its record shape or its photo host: `src/scanRunner.js`, `src/vehicleDetails.js`, `src/rescanSchedule.js` and `background.js` only ever call the functions below.

Adding a platform: one new file here, its line in `ADAPTERS` (before `schemaOrg`, which answers on any page that lists cars), a record or page of its shape in `test/fixtures/` and its entry in `PLATFORM_FIXTURES` in `test/adapters.test.js`. The contract test then checks everything in the table. No new permission: the site's own origin is what the popup already has (`activeTab`), the service origin is asked for by the wizard (`optional_host_permissions`), and a photo server is asked for by the side panel from the salesperson's click, with Chrome's own prompt (`src/photoHosts.js`; the owner approved this on 2026-09-29).

## The contract

| Function | What it does |
|---|---|
| `PLATFORM` | `{ id, name }`. `id` is the key stored on the site registry entry, the snapshot and the settings (`dealerInspire`, `schemaOrg`); `name` is what people see (the unsupported-page message lists every adapter's `name`: "What it reads today: Dealer Inspire; Standard vehicle data (schema.org)"). |
| `probeInPage()` | Runs **inside the dealer tab** (`chrome.scripting.executeScript`, world MAIN, injected by `scanRunner.probeTab` after the neutral `src/scan.js probeSiteInPage`). Returns this platform's `service` (whatever the adapter needs later: addresses, keys, status values) or `null` when the page is not this platform. The service is the adapter's own data: it is stored as-is on the site registry entry (`sites[origin].service`) and no code outside the adapter reads its fields. |
| `searchInPage(service, request)` | Runs **inside the dealer tab** (injected by `scanRunner.searchViaTab`): one request made the way the page's own code makes it, so no host permission is needed. Returns `{ ok: true, data }` or `{ ok: false, error }`. |
| `detect(probe)` | Does this adapter handle a probe? The probe is `{ site, service, adapterId }` from `scanRunner.probeTab`; `index.js detectAdapter` prefers `adapterId` (the probe that answered) and falls back to `detect`, which also finds the adapter for a stored service (`adapterForService`). No adapter's `detect` accepts another adapter's service (the contract test checks). |
| `origins(service)` | The host-permission patterns (`https://host/*`) background rescans need to reach the service directly. `src/rescanSchedule.js originsFor(site, list)` adds the website's own origin; it also accepts the stored service (the wizard and the popup pass it) and asks the site's adapter for the list. |
| `scanOptions(service)` | The options `scan` and `getDetails` need from the service (Dealer Inspire: `{ status: service.visibleStatusValues }`; schemaOrg: `{ origin, listUrl }`). `scanWithSearch` spreads it into `scan`'s options. |
| `scan(search, options)` | Reads the used and certified inventory through `search(request)`. Returns exactly `{ ok, fetchedAt, total, complete, requests, records, confirm: { checked, notFound, error } }` on success, plus three optional keys, each only when there are some: `unread` (the VINs of cars the website still lists whose details this scan did not read, such as a car page that answered 500; `scanWithSearch` keeps each one's entry from the last snapshot, so a bad server day neither drops the car nor changes it, and the adapter leaves them out of `confirm`), `pagesRead` (the VINs of cars whose own page this scan read; `scanWithSearch` stamps their snapshot entries with `pageReadAt`, carries the last stamp for the rest, and an adapter that can't read every page in one scan reads the oldest first) and `leftForLater` (the number of car pages a per-scan page limit left for the next scan; the warning says so instead of calling them unreadable). On failure it returns `{ ok: false, error, message, requests }`. `records` are the platform's own compact records (Dealer Inspire: `trimRecord`; schemaOrg: `{ node, url, facts }`). The options `scanWithSearch` passes besides `scanOptions`: `confirmVins` (VINs from the last scan and the posted list to double-check when they did not come back; `confirm.notFound` is the only "gone" signal), `confirmUrls` (`{ vin: url }`, each car's page as the last snapshot kept it, including the snapshot's `missingPages`: the last page of a car that was not in that scan, so a posted car that left the list on a bad server day is still checked at its page later), `lastSeen` (the last snapshot's entries) and `postedVins`. An adapter ignores what it doesn't need. Dealer Inspire also takes `vins` (only those cars) and `fullRecords` (every photo). |
| `getDetails(search, vin, options)` | One full record (every photo, description, features) for the post-time re-check, any inventory type so a car that became New is found and then refused: `{ ok, record, fetchedAt }` with `record: null` when the car is gone, or `{ ok: false, message }`. `options` is `scanOptions(service)` plus `url`, the car's page from the last snapshot, when the side panel knows it (`vehicleDetails.fetchVehicleDetails(tabId, vin, { url })` or `fetchVehicleDetailsDirect`). |
| `normalize(record)` | A platform record → the flat vehicle with exactly the fields in `src/vehicle.js VEHICLE_FIELDS` (one line per field says who reads it), or `null` without a VIN. Everything downstream (the pre-owned gate, the ready check, the rescan diff, the listing form, the description writer) reads only that shape. `location` is the store name exactly as the website gives it; `locationShort` is the normaliser's guess at the store's own part from brand words alone (`src/normalize.js shortLocation(location)`), because one record has no lot to compare with. `scanRunner.scanWithSearch` then settles every label over the lot's store names (`shortLocation(location, storeNames(vehicles))`: the words all stores share are the group and brand part, what differs is the short name), so nothing about one dealer's naming is baked in. A `descriptionRaw` of `null` (not `''`) means this scan did not read the car's description; `scanWithSearch` then keeps the lot-wide lines found before. |
| `makeDirectSearch(service)` | A `search(request)` that reaches the service from the extension (the service worker's background rescan and the side panel's re-check without a dealer tab; needs `origins(service)` granted). |
| `photoOrigins(records)` | The origins the lot's photos are hosted on, from a scan's records. Recorded on the site registry entry as `photoOrigins` by `performScan` and the background rescan. The adapter never asks for them: the side panel asks Chrome for a photo server the first time a car's photos need it. |

Two kinds of code in an adapter:

- `probeInPage` and `searchInPage` are copied into the page by Chrome, so they are **self-contained** (no imports, no identifier from outside the function body) and **read-only** (no clicks, no events, no form values, no submit). `test/adapters.test.js` runs both in a bare sandbox and checks they reach nothing in the module; `test/posting.test.js` checks the read-only rule and that `scanRunner.js` injects nothing else.
- Everything else never touches the page. It is given a `search(request)` from one of two places: `scanRunner.searchViaTab(tabId, adapter, service)` (the popup, the wizard and the post-time re-check: the call runs inside the tab through `searchInPage`) or `makeDirectSearch(service)` (the background rescan and the side panel's own list, with the host permission the wizard or the panel's click asked for).

Who calls what:

| Caller | Calls |
|---|---|
| `scanRunner.probeTab` | `probeSiteInPage` (neutral), then each adapter's `probeInPage` until one answers → `{ site, service, adapterId }` |
| `scanRunner.performScan` (popup Scan, wizard) | `detectAdapter`, `searchViaTab` → `searchInPage`, `scanOptions`, `scan`, `normalize` (then `shortLocation` over the lot's store names, and `matchStore` for the first-run store choice), `photoOrigins`; stores `{ adapter, service, photoOrigins }` on the site registry entry |
| `vehicleDetails.fetchVehicleDetails` (side panel, at post time) | `probeTab`, `scanOptions`, `getDetails` (with the car's known page as `url`), `normalize` |
| `vehicleDetails.fetchVehicleDetailsDirect` (side panel, a post from its own list or a dealer tab that can't be used) | `adapterById`, `origins` (permission check), `makeDirectSearch`, `scanOptions`, `getDetails`, `normalize` |
| `background.runRescan` (alarm, or the side panel's Rescan the website) | `adapterById`, `origins` (permission check), `makeDirectSearch`, `scanOptions`, `scan`, `normalize`, `photoOrigins` |
| `rescanSchedule.originsFor` (wizard, popup, worker) | `origins` through the site's adapter |

## Built

- **Dealer Inspire** (`dealerInspire.js` + `dealerInspireNormalize.js`): the Cars Commerce inventory search behind Dealer Inspire websites. Probe: `window.SEARCH_SERVICE` (`search` address, the site's own public `apiKey`, `visibleStatusValues`) and the page helper `window.IDPSearchServiceHelper.getListings`. Search: the helper when present, else the same `POST <search>/search` with `x-api-key`. Service host `websites-search.api.carscommerce.inc`; photo host seen so far `vehicle-images.carscommerce.inc` (the manifest's static image host). Verified on the pilot dealer's live site (2026-09-26/27) and mirrored by `test/e2e/mock-dealer-site.mjs`.
- **Standard vehicle data** (`schemaOrg.js`, on the two shared readers below): any website that publishes schema.org vehicle markup (JSON-LD or microdata) on its pages. It is last in `ADAPTERS`, so Dealer Inspire's own probe still wins on its sites. Written from the public schema.org definitions and Google's vehicle listing documentation and tested only on synthetic pages (`test/helpers.js standardSite`, `test/fixtures/structured/`, `test/e2e/mock-standard-site.mjs`). **No named platform is claimed**: which platforms it reads well is known only once a real site has been scanned, and then it is written here with the site and the date.
  - Probe: answers on a page that lists cars (vehicle nodes in its JSON-LD or microdata, or at least 2 links on the same website to car pages: an address with a VIN in it, or one that reads like a car page) or on one car's own page, never on Facebook. Service: `{ kind: 'schemaOrg', origin, listUrl }`, where `listUrl` is the list the probe ran on, or the used inventory page it links to.
  - Search: one GET of a page on the website, `{ url }` → `{ ok, status, finalUrl, redirected, contentType, text }`, the text capped at `PAGE_TEXT_LIMIT`. In the tab it is the page's own `fetch` with its defaults (no header of Lot Current's). From the worker it is sent without cookies. Both refuse to ask for an address off the website. A redirect the website itself answers with is followed the way a browser follows it (from the tab, cookies go only to the website's own origin; from the worker, none at all), and an answer that lands off the website is never used: it counts as an error (`test/adapters.test.js` checks this with two real local servers). `origins(service)` is the website itself, which the wizard already asks for, so rescans need no new permission.
  - Scan: the list and its `rel=next` pages (at most `MAX_LIST_PAGES`), then the sitemap named in `robots.txt` when the list's own count says it shows fewer cars than it holds. Only sitemap addresses shaped like this lot's own car pages are kept (`learnCarAddressShape`, learned from the website on every scan, never hard-coded). Then each car's page, `CONCURRENCY` (2) at a time, with no pauses and nothing random about the timing. A 403, a 429, a 503 or a bot check (on a page that answered 200, or on any other error page except a 404 or 410, which is the car's page gone) stops the scan with a message saying so, and so do `MAX_FAILED_IN_A_ROW` (3) car pages in a row that fail (a 500, a timeout, a reset connection). Nothing is retried and nothing is worked around.
  - Which pages it reads: the first scan reads every car's page. Later scans read new addresses, posted cars, cars without a price in the list's data, and cars whose list data no longer matches what their page said last time. The rest are taken from the list's data. At most `MAX_CAR_PAGES` car pages are read in one scan: posted cars first, then the pages read longest ago (the snapshot entry's `pageReadAt`; a car never read from its own page counts as oldest), so on a larger lot every car's page comes round within a few scans. A car whose page fails (5xx, a timeout, not a web page) keeps what its page said last time (`unread`); on the first scan, or for a car never read before, the list's data stands in, and a list that carries no price leaves that car on Not ready until its page reads. `total` is the number of car addresses found; `complete` means the list ended cleanly and every page to read was read.
  - Sold cars, as strict as Dealer Inspire's VIN lookup: a car missing from this scan is checked at the page the last snapshot kept for it. It is `notFound` only on a 404 or 410, SoldOut on its node, a redirect to a page without it, or a page with the website's own structured data but no node with its VIN. The last two count only once this website's car pages are known to carry their own car's VIN (a car page read this scan, or one sample page), because a car page that marks up only a "similar vehicles" carousel looks the same while its car is still for sale. Anything else (403, 429, 5xx, a timeout, a bot check, a page with no structured data, a file that isn't a web page) sets `confirm.error`, and the rescan marks nothing gone. `rescan.diffScans`'s "more than half of a 10+ car lot vanished" rule applies as it does for every adapter.
  - Limits:
    - A list page that draws its cars with scripts shows few or no links to a plain read of it. The scan then says it found no car links, or reads fewer cars; the sitemap helps only when the list states its own count.
    - A website that turns away reads without cookies fails the background rescan, and the popup shows "The last automatic rescan … failed" (or "The last rescan from the side panel … failed") with the website's answer; the side panel's re-check without a tab fails the same way and says to post from the popup on the website. The Scan button still reads it from the tab.
    - A list whose cards don't carry what the car's page does (a Carfax link, photos, a price) has those cars' pages read again on every scan.
    - A car's page that doesn't mark up its car leaves the list's data as all there is. On such a website a missing car can't be confirmed gone.
    - On a lot with more car pages to read than `MAX_CAR_PAGES`, a car whose page is not read this time keeps what its page said last time (or the list's data, for a car never read), the scan says how many pages were left for the next scan, and those are read first next time.

- **DealerOn** (`dealerOn.js`) and **Dealer.com** (`dealerCom.js`), both on the shared `inventoryJson.js`. Written from public sources (Dealer.com's Web Integration API documentation for its vehicle field names and price meanings; a public write-up of DealerOn's Cosmos list data: `DisplayCards[].VehicleCard` with `VehicleVin`, `VehicleYear`, `VehicleDetailUrl`, `VehicleInternetPrice`, `Mileage`) and the 2026-10-01 page-text survey of local dealer websites (server HTML read through a web-fetch tool, which sees no scripts; the notes are in the project's shared files, not in this repository): list pages drawn by scripts; DealerOn car pages carry the VIN in the address and photos at `/inventoryphotos/<id>/<vin>/ip/<n>.jpg`, a sold car's page answered 404 and robots.txt asks for `Crawl-delay: 10`; Dealer.com sold car pages answered 410. Tested on synthetic sites (`test/platformSites.js`, `test/e2e/mock-platform-sites.mjs`). **No real DealerOn or Dealer.com website has been read yet.**
  - Probe: the platform's marks (a list request below, scripts or styles from `dealeron.com` / `dealer.com`, a `dealeron.com` / `dealer.com` address, the page's `DDC` object on Dealer.com, the copyright or "Website by" line). The inventory address is the first request the page itself made to `/api/vhcliaa/vehicle-pages/cosmos/srp/vehicles/` (DealerOn) or to a `getInventory` / `ws-inv-data` address (Dealer.com) on its own origin, read from `performance.getEntriesByType('resource')`: nothing is guessed. Service: `{ kind, origin, inventoryUrl, listUrl }`; `inventoryUrl` is null on a page that made no such request (a car's page), and the scan then says to open the used inventory page and wait until the cars show. At post time, on a car's own page, `src/vehicleDetails.js` fills what the probe could not see from the service the last scan of this website stored, when the same adapter stored it.
  - Search: one GET on the website's own origin, `{ url }` → `{ ok, status, finalUrl, redirected, contentType, json, text }` (JSON parsed; a web page as text). From the tab it is the page's own `fetch` with its defaults; from the worker it is sent without cookies (`inventoryJson.directSearch`). An address off the website is refused before anything is sent. `origins(service)` is the website itself, so rescans need no new permission.
  - Scan: page 1 is the address the page called (its page number or start set back to the first page), then DealerOn's `pt` page number or Dealer.com's `start` offset, one request at a time, up to `MAX_INVENTORY_PAGES`, until the answer's stated count (`totalCount`, `TotalCount`...) is reached, a short or empty page ends the list, or a page adds no new car (the paging parameter didn't move the list: `complete` is false). A 401, 403, 429 or 503 stops the scan with the reason; a later page that fails keeps what was read, not complete.
  - Records: `{ card, origin, page? }`, the platform's own record. `findCards` takes the objects carrying a valid VIN in the answer's largest list (a featured list beside the lot's is not the lot), and later pages read the list at the same place as page 1; `pick` reads a field by its usual names (case and a `Vehicle` prefix ignored, `[{ name, value }]` attribute lists), and looks into nested objects only for the store name (Dealer.com's `address.accountName`), so a Carfax object's link or an offer's type is never the car's. Condition: the record's condition field, a `certified` flag (Certified Used), the address's condition word, and the title; a field that names a body ("SUV") is not a condition.
  - Prices (`choosePrices`): the price the platform marks final, or labels final / internet / sale / dealer / "<Dealer> Price", else a plain "Price", else the only base price. A "<Something> Price" counts as the dealer's only when every word before "Price" is in the dealership name the record carries; otherwise, next to a plain or base price, the car gets no price ("Two prices on the website"); the base amount below it ("Retail", plain "Price") is `priceBeforeFees`, so the dealer's price-basis setting chooses (default: the dealer's price, with its fee, as the surveyed sites show it). MSRP, Was, previous, payments, fees, rebates, discounts, conditional, employee/supplier/loyalty offers, wholesale, book, KBB, market and estimated values are never the price; two selling prices that disagree give no price ("Two prices on the website").
  - Sold cars: a car missing from the list is checked at the page the last snapshot kept: 404 or 410, not redirected, is gone. Any other readable answer (a page that still shows the car with a sold banner, a redirect), a car with no known page on the website, and the cars past `MAX_CONFIRM_PAGES` (12) in one scan are left unconfirmed: the rescan lists them as missing but not confirmed gone. A server error, a refusal or a failed request sets `confirm.error`, and the rescan then marks nothing gone. On DealerOn, whose robots.txt asks for 10 seconds between automated reads, those car-page reads keep a fixed 10-second gap (`PAGE_GAP_MS`); the list pages, a few requests per scan, do not wait.
  - getDetails: the list again (the car must still be in it, else `record: null`), then the car's own page for every photo and the description: its standard vehicle data for this VIN when it has some, and on DealerOn the `/inventoryphotos/` addresses with this car's VIN (thumbnails left out). Dealer.com car pages carry other cars' photos with nothing to tell them apart, so only the list's images and the page's standard data for this VIN are used.
  - Limits: the background rescan sends no cookies, so a website that turns such reads away fails the rescan (the Scan button still reads it from the tab); the list address is the first one the page asked for, so a list the person had filtered before the page first loaded is scanned filtered; the browser's resource timing list holds 250 entries by default, so on a very heavy page the list request may not be found (the scan then says to open the list page and wait); a missing car's sold check from the popup with the 10-second gap can take a couple of minutes, and closing the popup cuts it short (nothing is marked gone for the rest).
  - **What one survey run (`npm run survey`) must confirm before a dealer relies on these**, in order: (1) the list request's address and method (Dealer.com's may be a POST, which a GET cannot replay: the scan would stop with the website's answer), and which of its parameters are filters; (2) the paging parameter (`pt`, `start`) and the count field; (3) the record's field names for condition, certified, stock, mileage, photos and the labelled prices, and which price carries the doc fee; (4) DealerOn's photo addresses at full size; (5) a sold car's page answer on DealerOn. Fix what differs here and in the fixtures (`test/platformSites.js`), never in code outside this folder.

## Shared readers (not adapters)

- **Inventory data** (`inventoryJson.js`): the JSON a list page loads from its own website, read without knowing the platform's exact names (above, under DealerOn and Dealer.com). Pure, so the service worker runs it too; `scanInventory` and `detailsFor` are the scan and getDetails of an adapter that gives it a `pageAddress` and a `pagePhotos`.
- **Standard vehicle data** (`schemaOrgParse.js` + `schemaOrgNormalize.js`): the schema.org JSON-LD and microdata a website publishes for search engines (Car, Vehicle, MotorVehicle, Motorcycle, a Product with a VIN, and their Offer), written from the public schema.org definitions and Google's vehicle listing documentation. Pure and string-level, so the service worker can run it: `parseVehiclePage(html, pageUrl)` gives `{ vehicles, facts }`, and `normalizeVehicle(node, { url, facts })` gives the flat vehicle, or null without a valid VIN. A price is kept only when it is one US-dollar offer that the page's visible text also shows as its current price, not only crossed out (`<s>`, `<del>`, a line-through style) or after "Was", "MSRP", "List", "Retail", "Compare at", "Reg." or a payment's "based on". A `priceSpecification` typed StrikethroughPrice, ListPrice, MSRP, SRP, InvoicePrice or MinimumAdvertisedPrice, or priced per month or per unit, is never the price. An offer with no `priceCurrency` counts as US dollars only when the page shows that exact amount with a dollar sign. A price range, another currency and kilometres are left out with a reason (`readingNotes`). It has no probe or search of its own; `schemaOrg.js` is the adapter built on it. It names no platform: which platforms publish usable markup is known only once a real site has been scanned. Fixtures: `test/fixtures/structured/` (synthetic; see its `_about.md`).
