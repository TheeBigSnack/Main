# Dealer-website adapters

Every platform Lot Current reads lives here, one file per platform (plus a normaliser file next to it when that reads better), behind one contract. `index.js` lists the built adapters in `ADAPTERS`, in the order their in-page probes are tried. Nothing outside this folder knows a platform's name, its service, its record shape or its photo host: `src/scanRunner.js`, `src/vehicleDetails.js`, `src/rescanSchedule.js` and `background.js` only ever call the functions below.

Adding a platform: one new file here, its line in `ADAPTERS` (before `schemaOrg`, which answers on any page that lists cars), a record or page of its shape in `test/fixtures/` and its entry in `PLATFORM_FIXTURES` in `test/adapters.test.js`. The contract test then checks everything in the table. No new permission: the site's own origin is what the popup already has (`activeTab`), the service origin is asked for by the wizard (`optional_host_permissions`), and a photo server is asked for by the side panel from the salesperson's click, with Chrome's own prompt (`src/photoHosts.js`; the owner approved this on 2026-09-29).

## The contract

| Function | What it does |
|---|---|
| `PLATFORM` | `{ id, name, checkedLive? }`. `id` is the key stored on the site registry entry, the snapshot and the settings (one per adapter: `dealerInspire`, `dealerOn`, `dealerCom`, `schemaOrg`); `name` is what people see. `checkedLive: true` only once the reader has read a real dealership website (today Dealer Inspire); leave it out for a new reader, and set it in the same commit that records the survey run that confirmed it. The unsupported-page message (`index.js unsupportedSiteMessage()`) lists every adapter's `name` in `ADAPTERS` order, in two groups, so a new adapter appears in it with no other change: "Checked on a real dealership website: Dealer Inspire. Also tries, not yet checked on a real dealership website: DealerOn; Dealer.com; Standard vehicle data (schema.org)." |
| `probeInPage()` | Runs **inside the dealer tab** (`chrome.scripting.executeScript`, world MAIN, injected by `scanRunner.probeTab` after the neutral `src/scan.js probeSiteInPage`). Returns this platform's `service` (whatever the adapter needs later: addresses, keys, status values) or `null` when the page is not this platform. The service is the adapter's own data: it is stored as-is on the site registry entry (`sites[origin].service`) and no code outside the adapter reads its fields. |
| `searchInPage(service, request)` | Runs **inside the dealer tab** (injected by `scanRunner.searchViaTab`): one request made the way the page's own code makes it, so no host permission is needed. Returns `{ ok: true, data }` or `{ ok: false, error }`. |
| `detect(probe)` | Does this adapter handle a probe? The probe is `{ site, service, adapterId }` from `scanRunner.probeTab`; `index.js detectAdapter` prefers `adapterId` (the probe that answered) and falls back to `detect`, which also finds the adapter for a stored service (`adapterForService`). No adapter's `detect` accepts another adapter's service (the contract test checks). |
| `origins(service)` | The host-permission patterns (`https://host/*`) background rescans need to reach the service directly. `src/rescanSchedule.js originsFor(site, list)` adds the website's own origin; it also accepts the stored service (the wizard and the popup pass it) and asks the site's adapter for the list. |
| `scanOptions(service)` | The options `scan` and `getDetails` need from the service (Dealer Inspire: `{ status: service.visibleStatusValues }`; schemaOrg: `{ origin, listUrl }`). `scanWithSearch` spreads it into `scan`'s options. |
| `scan(search, options)` | Reads the used and certified inventory through `search(request)`. Returns exactly `{ ok, fetchedAt, total, complete, requests, records, confirm: { checked, notFound, error } }` on success, plus four optional keys, each only when there are some: `unread` (the VINs of cars the website still lists whose details this scan did not read, such as a car page that answered 500; `scanWithSearch` keeps each one's entry from the last snapshot, so a bad server day neither drops the car nor changes it, and the adapter leaves them out of `confirm`), `pagesRead` (the VINs of cars whose own page this scan read; `scanWithSearch` stamps their snapshot entries with `pageReadAt`, carries the last stamp for the rest, and an adapter that can't read every page in one scan reads the oldest first), `descriptionsUnread` (the VINs of this scan's cars whose description it did not read, such as a car taken from the list's data because nothing about it changed; their `descriptionRaw` is `null`, and `scanWithSearch` keeps the lot-wide lines found before and counts these cars in the lot when it judges a new one) and `leftForLater` (the number of car pages a per-scan page limit left for the next scan; the warning says so instead of calling them unreadable). On failure it returns `{ ok: false, error, message, requests }`. `records` are the platform's own compact records (Dealer Inspire: `trimRecord`; schemaOrg: `{ node, url, facts }`). The options `scanWithSearch` passes besides `scanOptions`: `confirmVins` (VINs from the last scan and the posted list to double-check when they did not come back; `confirm.notFound` is the only "gone" signal, and `confirm.error` means the check as a whole failed, so nothing is gone; an adapter that checks each car on its own may add `confirm.unchecked`, `{ vin: reason }`, only when some, for cars whose own check failed while the others' verdicts still stand (DealerOn and Dealer.com: a car page that answers a 5xx or from another website, or a request that fails outright): `diffScans` puts each under Needs a look with its reason), `confirmUrls` (`{ vin: url }`, each car's page as the last snapshot kept it, including the snapshot's `missingPages`: the last page of a car that was not in that scan, so a posted car that left the list on a bad server day is still checked at its page later), `lastSeen` (the last snapshot's entries) and `postedVins`. An adapter ignores what it doesn't need. Dealer Inspire also takes `vins` (only those cars) and `fullRecords` (every photo). |
| `getDetails(search, vin, options)` | One full record (every photo, description, features) for the post-time re-check, any inventory type so a car that became New is found and then refused: `{ ok, record, fetchedAt }` with `record: null` when the car is gone, or `{ ok: false, message }`. `record: null` means gone only after the adapter read the whole list: one whose list read stopped early (DealerOn and Dealer.com: a later page failed or was not inventory data, or the paging did not move the list on) adds `complete: false`, and `src/vehicleDetails.js` then says the list could not be read whole, never that the car is gone. A failure may say why: `refused: true` (a 403, 429, 503 or bot check: `vehicleDetails.js` asks the website nothing more), `carPage: true` (the car's own page or links failed or showed no data, so another list would not change the answer) and `noData: true` (the website still lists the car but its page has no vehicle data: not gone, and not the website turning Lot Current away). An adapter that does not say `refused` is read by its words: a 401, 403, 429 or 503 in its message, or a bot check, counts as one. `options` is `scanOptions(service)` plus `url`, the car's page from the last snapshot, when the side panel knows it (`vehicleDetails.fetchVehicleDetails(tabId, vin, { url })` or `fetchVehicleDetailsDirect`), and `carPages`, `[{ vin, url }]` for every car in that snapshot, which an adapter may use to tell the lot's other cars apart on a page (schemaOrg does). |
| `normalize(record)` | A platform record → the flat vehicle with exactly the fields in `src/vehicle.js VEHICLE_FIELDS` (one line per field says who reads it), or `null` without a VIN. Everything downstream (the pre-owned gate, the ready check, the rescan diff, the listing form, the description writer) reads only that shape. `location` is the store name exactly as the website gives it; `locationShort` is the normaliser's guess at the store's own part from brand words alone (`src/normalize.js shortLocation(location)`), because one record has no lot to compare with. `scanRunner.scanWithSearch` then settles every label over the lot's store names (`shortLocation(location, storeNames(vehicles))`: the words all stores share are the group and brand part, what differs is the short name), so nothing about one dealer's naming is baked in. A `descriptionRaw` of `null` (not `''`) means this read gave the car no description: a car the website gives no description (a list card without dealer comments) or one whose description the scan did not read, which `scan` lists in `descriptionsUnread` so `scanWithSearch` can tell the two apart. |
| `makeDirectSearch(service)` | A `search(request)` that reaches the service from the extension (the service worker's background rescan and the side panel's re-check without a dealer tab; needs `origins(service)` granted). |
| `photoOrigins(records)` | The origins the lot's photos are hosted on, from a scan's records. Recorded on the site registry entry as `photoOrigins` by `performScan` and the background rescan. The adapter never asks for them: the side panel asks Chrome for a photo server the first time a car's photos need it. |

Two kinds of code in an adapter:

- `probeInPage` and `searchInPage` are copied into the page by Chrome, so they are **self-contained** (no imports, no identifier from outside the function body) and **read-only**: they read the page and make the request, and never click, fire events, move focus or scroll, write to the page, its attributes, its cookie or its storage, navigate, or open a window or dialog. `test/adapters.test.js` runs both in a bare sandbox and checks they reach nothing in the module. `test/posting.test.js` searches their text for the usual spellings of those actions; the comment above its guard lists every method and property name it looks for, and a second test puts a line using each one into a real probe and expects it caught. A text search does not see a name built at run time, a property reached with brackets or an API not on that list, so a person reviewing a change to these functions still checks the rule. The same file checks that `scanRunner.js` injects nothing else.
- Everything else never touches the page. It is given a `search(request)` from one of two places: `scanRunner.searchViaTab(tabId, adapter, service)` (the popup, the wizard and the post-time re-check: the call runs inside the tab through `searchInPage`) or `makeDirectSearch(service)` (the background rescan and the side panel's own list, with the host permission the wizard or the panel's click asked for).

Who calls what:

| Caller | Calls |
|---|---|
| `scanRunner.probeTab` | `probeSiteInPage` (neutral), then each adapter's `probeInPage` until one answers → `{ site, service, adapterId }` |
| `scanRunner.performScan` (popup Scan, wizard) | `detectAdapter`, `searchViaTab` → `searchInPage`, `scanOptions`, `scan`, `normalize` (then `shortLocation` over the lot's store names, and `matchStore` for the first-run store choice), `photoOrigins`; stores `{ adapter, service, photoOrigins }` on the site registry entry |
| `vehicleDetails.fetchVehicleDetails` (side panel, at post time) | `probeTab`, `scanOptions`, `getDetails` (with the car's known page as `url`), `normalize` |
| `vehicleDetails.fetchVehicleDetailsDirect` (side panel, a post from its own list or a dealer tab that can't be used) | `adapterById`, `origins` (permission check), `makeDirectSearch`, `scanOptions`, `getDetails`, `normalize` |
| `background.runRescan` (alarm, or the side panel's Rescan the website) | `adapterById`, `origins` (permission check), `makeDirectSearch`, `scanOptions`, `scan`, `normalize`, `photoOrigins` |
| `rescanSchedule.originsFor` (wizard, popup, worker) | `origins` through the site's adapter |

## Built

- **Dealer Inspire** (`dealerInspire.js` + `dealerInspireNormalize.js`): the Cars Commerce inventory search behind Dealer Inspire websites. Probe: `window.SEARCH_SERVICE` (`search` address, the site's own public `apiKey`, `visibleStatusValues`) and the page helper `window.IDPSearchServiceHelper.getListings`. Search: the helper when present, else the same `POST <search>/search` with `x-api-key`. Service host `websites-search.api.carscommerce.inc`; photo host seen so far `vehicle-images.carscommerce.inc` (the manifest's static image host). Verified on the pilot dealer's live site (2026-09-26/27) and mirrored by `test/e2e/mock-dealer-site.mjs`. Every answer must carry a `listings` array, and an empty one counts only when the answer also says `total_vehicle_count: 0` (`listingsOf`): a 200 that is an error object, or a page helper that resolved nothing, fails the scan (the paged read) or sets `confirm.error` (the VIN lookup), so such an answer never calls a car gone, on a lot of any size.
- **Standard vehicle data** (`schemaOrg.js`, on the two shared readers below): any website that publishes schema.org vehicle markup (JSON-LD or microdata) on its pages. It is last in `ADAPTERS`, so Dealer Inspire's own probe still wins on its sites. Written from the public schema.org definitions and Google's vehicle listing documentation and tested only on synthetic pages (`test/helpers.js standardSite`, `test/fixtures/structured/`, `test/e2e/mock-standard-site.mjs`). **No named platform is claimed**: which platforms it reads well is known only once a real site has been scanned, and then it is written here with the site and the date.
  - Probe: answers on a page that lists cars (vehicle nodes in its JSON-LD or microdata, or at least 2 links on the same website to car pages: an address with a VIN in it, or one that reads like a car page) or on one car's own page, never on Facebook. Service: `{ kind: 'schemaOrg', origin, listUrl }`, where `listUrl` is, in order: the list the probe ran on when its own address reads as used inventory and names no part of the lot (below); the used inventory page it links to when that link reads as the whole used list (its words say so, "Used", "Shop pre-owned", or its address is only inventory words, `/used-vehicles/`, `/inventory/?condition=used`); the page it ran on when its title names used cars and not new ones, its address names no part of the lot, and it is not the site's home page (`/`, `/index.html`; a lot that sells only used cars, its list at `/inventory/` titled "Used Vehicles for Sale"; a home page titled "New & Used Cars" with a few featured cars is not the used list); a link with a used word and an inventory word in its address (`/used-cars-<town>/`); else the page it ran on. The shortest link of each kind. A link is never the list when its query holds anything but values that select used cars (certified ones too, beside a value that selects used ones: `/inventory/?condition=used&condition=certified`) and a page number or sort order, told by the parameter's name (`page`, `p`, `pg`, `start`, `sort`, `sortby`, `order`, `orderby`, `dir` and the like), so a filtered list (`/used-cars/?make=Jeep`, `/inventory/?condition=used&make=Jeep`, `/used-vehicles/?condition=certified`) is not, whatever its link text; nor when its address names part of the lot with a word the probe knows (`SUBSET_WORDS`: a make, `/used-jeep-cars/`, `/used-jeep-wrangler/`, every make the VIN check knows among them; certified cars, `/certified-pre-owned-vehicles/`; a body style, a fuel, a price range or a deal, `/used-cars-under-15000/`); nor when it is for selling, trading in or valuing a car (`/sell-your-used-car/`). A town that shares a make's name (`/used-cars-lincoln/`) is taken for part of the lot, so the probe keeps to the page it ran on (on a car's page, the list stays unknown); a page about part of the lot named only with words the probe doesn't know (`/used-wrangler-inventory/`) can still be taken, and the link text never stands in for the inventory word its address lacks. on a car's own page with no other used link, the list stays unknown until a scan from the used inventory page. On page 2 of the list, or a sorted or filtered list, it is the same list with fewer of its query parameters when the page links to it (its "Used" link, its first page); a parameter is never removed by name, so one that selects used cars stays.
  - Search: one GET of a page on the website, `{ url }` → `{ ok, status, finalUrl, redirected, contentType, text }`, the text capped at `PAGE_TEXT_LIMIT`. In the tab it is the page's own `fetch` with its defaults (no header of Lot Current's). From the worker it is sent without cookies. Both refuse to ask for an address off the website. A redirect the website itself answers with is followed the way a browser follows it (from the tab, cookies go only to the website's own origin; from the worker, none at all), and an answer that lands off the website is never used: it counts as an error (`test/adapters.test.js` checks this with two real local servers). `origins(service)` is the website itself, which the wizard already asks for, so rescans need no new permission.
  - Scan: the list from its first page (a stored list address past page 1 is followed back along its `rel=prev` links; when that way back breaks, the read starts at the earliest page reached and is not complete; when it comes round to where it started, a first page that names the last as the one before, the read starts there and is complete only once the forward read has reached every page the way back did) and its `rel=next` pages (at most `MAX_LIST_PAGES`), then the sitemap named in `robots.txt` when the list's own count says it shows fewer cars than it holds. `robots.txt` is read only for its `Sitemap` lines (the first 500 KB of it, as search engines read it): its `Disallow` and `Crawl-delay` lines are not applied to these reads, unlike the survey (`docs/survey.md`) and DealerOn's fixed gap below. Whether a dealer's own authorisation to read its website (the Dealer Subscription Agreement) stands in for them, or this reader should obey them too, is an open question for the owner. Only sitemap addresses shaped like this lot's own car pages are kept (`learnCarAddressShape`, learned from the website on every scan, never hard-coded). A link that only reads like a car page is kept when it has the shape of the links with a VIN, or, with fewer than two of those, always; an address with a file ending (`.pdf`, an image) is never a car page. Each car is counted once and read at one address first (`oneAddressPerCar`): when its card also links forms or files about it with its VIN in the address (financing, "Check availability", a window sticker), the address the list's own data names for the car comes first, then the page the last read of the car came from, then one with the VIN in its path, then the first the list links. When that first address is neither the list's nor the last read's and turns out not to be the car's page (a form, a page without the car's node, a file, a 404, or a link that fails: one that sends Lot Current to another website, a 500, JSON), its other addresses are read in turn, at most `MAX_ADDRESSES_PER_CAR` (4) in all; the scan learns as it goes which kind of address gives cars on this website (from the last scan's pages first) and tries that kind first, and tries a kind that twice gave no car last; such a kind is skipped for a car only once that car's page of a kind that gives cars has been read, so car pages without vehicle data first on the list (cars in transit) never stop the later cars' own pages being read. A page of the kind that gives cars that fails ends that car's turn, and a car found at a later address after another link failed is not a failed page. Nor is a car whose page of a kind that gives cars answered without vehicle data (a car in transit) or as gone (404, 410) while another of its links failed (a form that answers 500): that page answers for the car. A car read before any kind of address has given a car, one of its links failing and another answering, is settled that way once the reading is done (when the answering page turns out to be of the kind that gives cars), and otherwise as a car not read this time. A car left with addresses unread, none of those read being its page, keeps its last reading and the scan is not complete. At post time without the car's known page (`getDetails`), the links with its VIN are read the same way, those with the VIN in their path first, until one shows the car; a link that fails is passed over, and when no link shows the car the first failure is the answer (a refusal stops at once); when its page may be among links left unread, the re-check says so instead of calling the car gone. A car whose only addresses answered with a file (a PDF, an image), known to neither the list's data nor the last scan, is not a car and not a failed page; a page that answers plain text or JSON is a failed page. When such files had the VIN in their path and links that read like car pages were left out for not having their shape, the scan is not complete; so it is when the links with a VIN showed no car more often than they gave one (forms that carry the VIN where the car pages don't, even beside one car page that carries its VIN), beside such left-out links, and whenever it counted cars and gave none. Those left-out links are not read in their place: on a lot like that the scan reads no car and says so. Then each car's page, `CONCURRENCY` (2) at a time, with no pauses and nothing random about the timing. A 403, a 429, a 503 or a bot check (on a page that answered 200, or on any other error page except a 404 or 410, which is the car's page gone) stops the scan with a message saying so, and so do `MAX_FAILED_IN_A_ROW` (3) cars in a row whose pages fail (a 500, a timeout, a reset connection); a car whose failing link is not of the kind that gives cars while another of its addresses answered is not counted, so on a lot where no kind of address has given a car yet a run of cars like that never stops the scan (it reads each car's addresses, at most `MAX_ADDRESSES_PER_CAR`, and ends not complete when none of those pages turns out to be the cars' kind). Nothing is retried and nothing is worked around.
  - Which pages it reads: the first scan reads every car's page. Later scans read new addresses, posted cars, cars without a price in the list's data, and cars whose list data no longer matches what their page said last time. The rest are taken from the list's data. At most `MAX_CAR_PAGES` car pages are read in one scan: posted cars first, then the pages read longest ago (the snapshot entry's `pageReadAt`; a car never read from its own page counts as oldest), so on a larger lot every car's page comes round within a few scans. A car whose page fails (5xx, a timeout, not a web page) keeps what its page said last time (`unread`); on the first scan, or for a car never read before, the list's data stands in, and a list that carries no price leaves that car on Not ready until its page reads. `total` is the number of car addresses found; `complete` means the list ended cleanly and every page to read was read.
  - Sold cars, as strict as Dealer Inspire's VIN lookup: a car missing from this scan is checked at the page the last snapshot kept for it. It is `notFound` only on a 404 or 410, SoldOut on its node, a redirect to a page without it, or a page with the website's own structured data but no node with its VIN. The last two count only once this website's car pages are known to carry their own car's VIN (a car page read this scan, or one sample page), because a car page that marks up only a "similar vehicles" carousel looks the same while its car is still for sale. A refusal (403, 429, 503, a bot check) sets `confirm.error`, and the rescan marks nothing gone. Any other failure (another 5xx, a timeout, a page with no structured data, a file that isn't a web page, an answer from another website) leaves only that car unchecked: it goes in `confirm.unchecked` with the reason, the other missing cars are still checked and their verdicts still count, and the rescan lists it under Needs a look saying why, so one car's broken page, checked again on every scan while someone still has it posted, never holds back another sold car. When the sample page shows that this website's car pages don't mark up their own car, only the "page without it" verdicts become unchecked; a 404, 410 or SoldOut still counts. Cars the last snapshot listed are checked first, and after three failed pages in a row the rest wait for the next scan. The snapshot keeps the cars a check left unchecked (`unchecked`), and `scanRunner.scanWithSearch` sends them last in the next scan's `confirmVins`, for every adapter, the ones the check never reached before those whose page failed, so a few pages that keep failing never hold back the other cars' sold check. `rescan.diffScans`'s "more than half of a 10+ car lot vanished" rule applies as it does for every adapter.
  - Limits:
    - A list opened past its first page, or filtered, that neither links to its start or its unfiltered form nor names the page before it with `rel=prev`, is read from where it was opened, and nothing tells it apart from the whole list: scan from the used inventory page itself. So is a filtered list whose address has no used word (taken as the list by its title): only its page number is undone, through `rel=prev`, since which of its parameters selects used cars can't be told from their names.
    - A list page that draws its cars with scripts shows few or no links to a plain read of it. The scan then says it found no car links, or reads fewer cars; the sitemap helps only when the list states its own count.
    - A website that turns away reads without cookies fails the background rescan, and the popup shows "The last automatic rescan … failed" (or "The last rescan from the side panel … failed") with the website's answer; the side panel's re-check without a tab fails the same way and says to post from the popup on the website. The Scan button still reads it from the tab.
    - A list whose cards don't carry what the car's page does (a Carfax link, photos, a price) has those cars' pages read again on every scan.
    - A car's page that doesn't mark up its car leaves the list's data as all there is. On such a website a missing car can't be confirmed gone.
    - On a lot with more car pages to read than `MAX_CAR_PAGES`, a car whose page is not read this time keeps what its page said last time (or the list's data, for a car never read), the scan says how many pages were left for the next scan, and those are read first next time.

- **DealerOn** (`dealerOn.js`) and **Dealer.com** (`dealerCom.js`), both on the shared `inventoryJson.js`. Written from public sources (Dealer.com's Web Integration API documentation for its vehicle field names and price meanings; a public write-up of DealerOn's Cosmos list data: `DisplayCards[].VehicleCard` with `VehicleVin`, `VehicleYear`, `VehicleDetailUrl`, `VehicleInternetPrice`, `Mileage`) and the 2026-10-01 page-text survey of local dealer websites (server HTML read through a web-fetch tool, which sees no scripts; the notes are in the project's shared files, not in this repository): list pages drawn by scripts; DealerOn car pages carry the VIN in the address and photos at `/inventoryphotos/<id>/<vin>/ip/<n>.jpg`, one sold car's page answered 404 (a single page, still to confirm: item 5 below) and robots.txt asks for `Crawl-delay: 10`; Dealer.com sold car pages answered 410 (seven pages). Tested on synthetic sites (`test/platformSites.js`, `test/e2e/mock-platform-sites.mjs`). **No real DealerOn or Dealer.com website has been read yet.**
  - Probe: the platform's marks (a list request below, scripts or styles from `dealeron.com` / `dealer.com`, a `dealeron.com` / `dealer.com` address, the page's `DDC` object on Dealer.com). A credit line alone never decides, since any page can name a platform: on DealerOn the copyright line counts only beside one of DealerOn's own files on the website itself (a `/vhcliaa/` path, as the Cosmos list's files and data use, or `dealeron-js.aspx`), and Dealer.com's "Website by" line does not count. The inventory address is the first request the page itself made to `/api/vhcliaa/vehicle-pages/cosmos/srp/vehicles/` (DealerOn) or to a `getInventory` / `ws-inv-data` address (Dealer.com) on its own origin, read from `performance.getEntriesByType('resource')`: nothing is guessed. Service: `{ kind, origin, inventoryUrl, listUrl }`; `inventoryUrl` is null on a page that made no such request (a car's page), and the scan then says to open the used inventory page and wait until the cars show. At post time, on a car's own page, `src/vehicleDetails.js` fills what the probe could not see from the service the last scan of this website stored, when the same adapter stored it; when the last scan used another adapter than the one whose probe answers on the open page (a car's page that shows standard vehicle data and no mark of this platform), the last scan's adapter reads the car with its stored service, so the price is chosen as the scan chose it. A car missing from the list the open page loaded (the new cars, a search filtered for a customer), or a read of that list that failed on its first page or found no cars there, is not the answer: `src/vehicleDetails.js` reads the car once more, through the same tab, with the service the last scan stored, and only that answer is final. After a refusal (401, 403, 429, 503) nothing more is asked.
  - Search: one GET on the website's own origin, `{ url }` → `{ ok, status, finalUrl, redirected, contentType, json, text }` (JSON parsed; a web page as text). From the tab it is the page's own `fetch` with its defaults; from the worker it is sent without cookies (`inventoryJson.directSearch`). An address off the website is refused before anything is sent. `origins(service)` is the website itself, so rescans need no new permission.
  - Scan: page 1 is the address the page called (its page number or start set back to the first page), then DealerOn's `pt` page number or Dealer.com's `start` offset, one request at a time, up to `MAX_INVENTORY_PAGES`, until the answer's stated count (`totalCount`, `TotalCount`...) is reached, a short or empty page ends the list, or a page adds no new car (the paging parameter didn't move the list: `complete` is false). A 401, 403, 429 or 503 stops the scan with the reason; a later page that fails keeps what was read, not complete.
  - Records: `{ card, origin, page? }`, the platform's own record. `findCards` takes the objects carrying a valid VIN in the answer's largest list (a featured list beside the lot's is not the lot), and later pages read the list at the same place as page 1; `pick` reads a field by its usual names (case and a `Vehicle` prefix ignored, `[{ name, value }]` attribute lists), and looks into nested objects only for the store name (Dealer.com's `address.accountName`), so a Carfax object's link or an offer's type is never the car's. Condition: the record's condition field, a `certified` flag (Certified Used), the address's condition word, and the title; a field that names a body ("SUV") is not a condition. A demo or loaner word in any of the record's condition fields (`conditionFields`: not only the first one present, so `type: Loaner` beside `inventoryType: used` counts), however the platform writes it ("Service Loaner", "SERVICE_LOANER", "ServiceLoaner", "DEMO_UNIT"), sets `isDemo` / `isLoaner` like the platform's own flags, and a `certified` flag never renames it, so a certified service loaner still meets the gate as a loaner; its certified mark (the flag, or a certified word in a condition field, "Certified Loaner") is kept beside it as the second condition field (`readableType: 'Certified'`), which the gate counts for a demo or loaner whatever the title opens with, so a car the website calls both certified and a loaner or demo goes to Needs a look, or is skipped as sold as new when its title or address also calls it new (a note then names the mark); it is never Ready and never Certified Used (a plain certified car gets no second sign from its mark). A new word counts in any condition field too, when the field reads as a new condition ("New", "Brand New", "New Vehicle", "NEW_VEHICLE", or a code in one word, "NEWVEHICLE", read as "NEW VEHICLE"; never a grade or a badge that holds the word, "Like New", "New Arrival"): it stops the certified rename, and a record that says used in one field and new in another keeps the second word as `readableType`, so the gate (`classify.js checkPreOwned`) sends the car to Needs a look naming both words. Mileage (`mileageOf`): a bare number is miles, as these US platforms send it; a number written with a unit, or beside a unit field, counts only in miles; kilometres are never converted and any other unit is no mileage, so the car waits on Needs a look.
  - Prices (`choosePrices`): the price the platform marks final, or labels final / internet / sale / dealer / "<Dealer> Price", else a plain "Price", else the only base price. A "<Something> Price" counts as the dealer's only when every word before "Price" is in the dealership name the record carries (`isDealerPrice`); when one of those words otherwise says a figure is not the price ("Kelley Chevrolet", "Old Town Ford", "Value Auto Mart"), the words must open the name, as DealerOn (the whole name) and Dealer.com (its first word) write it, so "Kelley Price" at "Kelley Chevrolet" is the dealer's price and "Market Price" at "Auto Market of Springfield" is not; otherwise, next to a plain or base price, the car gets no price ("Two prices on the website"); the base amount below it ("Retail", plain "Price") is `priceBeforeFees`, so the dealer's price-basis setting chooses (default: the dealer's price, with its fee, as the surveyed sites show it). MSRP, Was, previous, payments, fees, rebates, discounts, conditional, employee/supplier/loyalty offers, wholesale, book, KBB, market and estimated values are never the price (a broader list than the shared guide words on purpose: a labelled figure the reader can't place waits on a person, so "Value Price" alone is "Call for price" here while the standard-data reader takes "Value Price $24,995" in page text as the price); two selling prices that disagree give no price ("Two prices on the website"). A guide's value, an estimate or an offer for the car, by the standard-data reader's own word list (`schemaOrgNormalize.js` `GUIDE_PRICE_WORDS`: "Market Price", "KBB Value", "Fair Purchase Price", "Trade-In Value", "Instant Cash Offer" and the like), is never the price whatever words sit beside it ("Your Cash Offer", even marked final; the words of a phrase may be joined by a space, a hyphen or nothing, "Cash-Offer"), and so is a label that ends in "Offer" ("Sell Us Your Car Offer", "Your Carvana Offer", "Our Offer") unless the website's own selling words name it ("Internet Offer", "Sale Offer"); when a record has no other price the car gets none and the label quotes it for a person to check (`the list labels its price "Market Price", which Lot Current does not read as the selling price`), as on standard-data websites: some websites label their own selling price that way. Only a label that is such a figure is quoted (the guide's words at its end, or followed by "price", "value" or "offer", or an offer's label), never a payment or an incentive named after one ("Estimated Payment", "Trade-In Bonus"). A field named for such a figure with no "price" in its name (`VehicleMarketValue`, `kbbValue`, `tradeInValue`) is read for that quote too, and never as the price. A record that labels its price in a field of its own (`ownPriceLabel`: a top-level `PriceLabel`, `PriceTitle` or `PriceCaption`, with or without the `Vehicle` prefix; DealerOn's `VehiclePriceLabel` in the fixtures) is read as that label: when it names something other than the selling price ("Market Value", "Instant Cash Offer", "MSRP", a payment) and is not the dealership's own "<Dealer> Price" as above, the car gets no price, whatever the price fields are called and whatever else the record carries, and the label is quoted. The price the platform marks final (Dealer.com's `isFinalPrice`) is read the same way: when its label or its `typeClass` is set aside as not the price (an offer, "Special Offer" and "Today's Offer" included, a guide's value, an MSRP, a conditional or employee price), the website's price is that figure, so the car gets no price and the label is quoted, never the plain or base price beside it (Not ready: `No price on the website (the list labels its price "Special Offer", which Lot Current does not read as the selling price)`). Every one of these label tests reads the label without the footnote and trademark marks a website puts after it (`labelWords`: "Your Carvana Offer*", "Our Offer™", "Market Value†", "Sample Price¹", and a footnote written as a number in brackets, "(1)", a mark with a number, "*1", a number in a superscript tag, "<sup>1</sup>", other HTML tags or HTML entities, "&#42;", "&trade;"; a bare number at the end stays part of the label), so a mark never turns an offer into a selling price or a dealer's own price into an unknown one; a quoted label keeps its marks as the website writes it. The website's own price written in a way that is not a plain amount ("$40,590*", "Call for Price", "$24,499 + tax", nothing at all) is kept as an unreadable entry (`labeledPrices`: `{ value: null, text }`; any entry or field the platform marks final, and a field or entry named for a selling price ending in "price" that holds text, never a flag such as `isFinalPrice` or `showInternetPrice`): the final one, unless a final price that reads stands beside it, or a selling one when no final price reads, gives the car no price, quoted (Not ready: `No price on the website (the list's final price reads "$40,590*", which Lot Current does not read as an amount)`), never the plain, base or starting price beside it; and a record whose own label says its price is the dealer's or a selling one ("Sample Motors Price") with only a base amount that reads gets none either (`the list labels its price "Sample Motors Price" but gives no amount Lot Current can read for it`). A final entry with no label is the price when its amount reads.
  - Sold cars: a car missing from the list is checked at the page the last snapshot kept: 404 or 410, not redirected, is gone. Any other readable answer (a page that still shows the car with a sold banner, a redirect), a car with no known page on the website, and the cars past `MAX_CONFIRM_PAGES` (12) in one scan are left unconfirmed: the rescan lists them as missing but not confirmed gone. A car page that fails on its own (a 5xx, an answer from another website, or a request that fails outright, as a page redirecting to another website does in the browser) leaves only that car unconfirmed, in `confirm.unchecked` with the reason in the standard-data reader's words ("its page gave HTTP 500", "its page could not be read (...)", "its page sent Lot Current to another website (...)"), which the rescan quotes in the car's Needs a look item; after `MAX_FAILED_IN_A_ROW` (3) such pages in a row the check stops for this scan, and the next scan checks the cars it did not reach before those whose page failed (`scanRunner.confirmOrder`). A refusal (401, 403, 429, 503) sets `confirm.error`, and the rescan then marks nothing gone. When more than one car page is to be read, the scan first reads the website's robots.txt once and keeps the `Crawl-delay` it gives every robot as a fixed gap between those reads (none when it gives none; a website asking for more than `MAX_PAGE_GAP_MS`, 10 seconds, gets one car page per scan; a robots.txt that turns the read away stops the check and marks nothing gone). When robots.txt can't be read, comes from another website or is a web page answering for it, the platform's own gap applies: 10 seconds on DealerOn (`PAGE_GAP_MS`, what its sites asked for in the survey), none on Dealer.com. The list pages, a few requests per scan, do not wait.
  - getDetails: the list again (the car must still be in it, else `record: null` with the list read's `complete`, `false` when a later page failed, was not inventory data or repeated the first), then the car's own page for every photo and the description: its standard vehicle data for this VIN when it has some, and on DealerOn the `/inventoryphotos/` addresses with this car's VIN (thumbnails left out). Dealer.com car pages carry other cars' photos with nothing to tell them apart, so only the list's images and the page's standard data for this VIN are used.
  - Limits: the background rescan and the side panel's re-check without a dealer tab send no cookies, so a website that turns such reads away fails the rescan, or stops the post with the note to post from the popup on the website (the Scan button still reads it from the tab); the list address is the first one the page asked for, so a list the person had filtered before the page first loaded is scanned filtered; the browser's resource timing list holds 250 entries by default, so on a very heavy page the list request may not be found (the scan then says to open the list page and wait); a missing car's sold check from the popup with the 10-second gap can take a couple of minutes, and closing the popup cuts it short (nothing is marked gone for the rest).
  - **What one survey run (`npm run survey`) must confirm before a dealer relies on these**, in order: (1) the list request's address and method (Dealer.com's may be a POST, which a GET cannot replay: the scan would stop with the website's answer), and which of its parameters are filters; (2) the paging parameter (`pt`, `start`) and the count field; (3) the record's field names for condition, certified, stock, mileage, photos and the labelled prices, and which price carries the doc fee, and whether the amounts are plain ones (the report's "price labels" line marks a price "not an amount the reader can read", which leaves the car with no price; the report's "condition fields" line shows each condition field's words, so a loaner or demo spelling the reader does not know shows there); (4) DealerOn's photo addresses at full size; (5) a sold car's page answer on DealerOn; (6) whether the records label their price in a field of their own, and what it says (the report's "the records' own label for their price" line): a guide's or an offer's label there ("Market Value") leaves every such car with no price, and a label field under another name is not read yet. Fix what differs here and in the fixtures (`test/platformSites.js`), never in code outside this folder.

## Shared readers (not adapters)

- **Inventory data** (`inventoryJson.js`): the JSON a list page loads from its own website, read without knowing the platform's exact names (above, under DealerOn and Dealer.com). Pure, so the service worker runs it too; `scanInventory` and `detailsFor` are the scan and getDetails of an adapter that gives it a `pageAddress` and a `pagePhotos`.
- **Standard vehicle data** (`schemaOrgParse.js` + `schemaOrgNormalize.js`): the schema.org JSON-LD and microdata a website publishes for search engines (Car, Vehicle, MotorVehicle, Motorcycle, a Product with a VIN, and their Offer), written from the public schema.org definitions and Google's vehicle listing documentation. Pure and string-level, so the service worker can run it: `parseVehiclePage(html, pageUrl)` gives `{ vehicles, facts }`, and `normalizeVehicle(node, { url, facts })` gives the flat vehicle, or null without a valid VIN. A price is kept only when it is one US-dollar offer that the car's own visible text also shows as its current price, not only crossed out (`<s>`, `<del>`, a line-through style, a class the page's own style rules strike through, or a class named for it, read word by word: "strike", "old-price", "price-was") or after "Was", "MSRP", "List", "Retail", "Compare at", "Reg.", a payment's "based on", or a guide's, an estimate's or an offer's words ("KBB", "Kelley Blue Book", "Fair Purchase Price", "Typical Listing Price", "Market value", "Market price", "Book value", "Trade-in value", "NADA", "J.D. Power", "Black Book", "Instant Cash Offer", "Instant Offer", "Trade-in offer", "Edmunds", "Estimated value", "Window sticker"; the guide's, estimate's and offer's words are `GUIDE_PRICE_WORDS`, shared with the inventory-data reader). When the page's only price carries such words, the car still gets no price, and the reason quotes them for a person to check (`the page labels its only price "Market Price", which Lot Current does not read as the selling price`): some websites label their own selling price that way. The car's own text (`schemaOrg.js factsForCar`, from the segments `parseVehiclePage` ties to each car's card): a card is the largest element whose links to cars all go to one car, inside one that links to another car or shows something else, so a tile's "Check availability", financing or trade-in links don't split it. So when a car's page holds exactly one other car's tile in the same block as its own price box (the car's title in a bar of its own), the whole block is that tile's card: the car gets no price there, and To do or Needs a look says the page does not show its price, but the tile's price never passes for the car's. Lot Current cannot tell such a price box from a piece of the tile by the page's structure, so it does not try. A layout known to be read wrong, so that another car's tile at the car's old markup price can pass for the car's price: a tile with no element of its own whose price sits loose in the page outside every element that holds a car link (that price is the page's own text). Which car a link goes to is `schemaOrg.js carKeys`: the VIN in its address (a form with the VIN in its query goes with that car), the car this page's markup names at that address, a car page the list named (or one of those addresses with a query added, "?srp=1", when the car's own address has none), or an address that reads like a car page (new or used). On one car's own page (the car the page is read for, whatever address its markup gives, else the car its markup puts at this address), such an address names another car only by a word that tells cars apart: a word with a digit that is neither a model year nor one of the car's own words (another car's stock number or id, also in the query, where a number of one or two digits counts for nothing: "?srp=1"); a model year other than the car's; a make other than the car's (every make the VIN check knows, every other make the probe names and a few more, also in two words: "land rover"); or, in an address about new cars at another model year, any word that is neither the car's own nor a search's ("/new/2027-honda-civic-sport/", while "Shop new 2027 Honda Civic" is a search). The car's own words are its make or its short name ("Chevy"), model (also run together, "f150" for an F-150), trim, body, drive and stock number. What a search adds counts for nothing: the values of a tracking, campaign, place, sorting, price or mileage query ("?utm_campaign=fall2026", "?zip=43215", "?radius=100", "?sort=price"), a door, drive or engine word ("4dr", "4x4", "v6"), and, except in an address about new cars at another model year, any word without a digit ("near-me", "hybrid"). When the address otherwise reads as the car's own search (no word without a digit but the car's own and a search's), neither does a one-digit page number after "page" or "pg" ("/page/3/"), a round price limit ("-under-20000", "-under-20k") or a range of at most ten model years with the car's in it ("2014-2018"), as long as the word before the number is a search's and not one of the car's own (on a Ford Expedition MAX's page, "max" is its model's, so "/used/2018-ford-expedition-max-17500/" is another car's stock number). In any other address those numbers count as they are, so another car's stock number after a word a search also uses ("/used/2018-ford-expedition-max-12345/" on a Ford Escape's page, "-p-123", "-max-88001") still tells it apart. So a "See all 2016 Honda Civic" search, a breadcrumb or another address of the same car is no car and never makes the car's own price box another car's card, and another car's tile linked with its stock number or id, another model year, another make the list holds, a model with a digit in its name ("f250"), or a new car's other model or trim does not pass for this car's text. Not told apart this way: a tile whose address has no stock number or id, no other make the list holds and no model with a digit, at this car's model year or with no model year at all ("/used/2016-honda-civic-ex/", "/used/2016-honda-accord/", "/used/2016-accord/" or "/used/honda-accord/" on a 2016 Honda Civic's page), or about new cars at another year with no word but the car's own and a search's ("/new/2027-honda-civic/"); a tile linked to this car's own model search with a number under a search's query name or a one-digit page number ("/used/2016-honda-civic/?miles=88001", "/used/2016-honda-civic/page/5/" on a 2016 Honda Civic's page), which reads as a search; and a tile linked through an address that neither reads like a car page nor is one the last scan kept ("/inventory/SM1001/" on a lot whose car pages carry their VIN). The other way round, a model search in the car's price box makes the box another car's card, and the car gets no price, when it holds any other word with a digit ("?promo=fall2026", a page number of two digits in its path, a price limit that is not round, "-under-15995") or, about new cars at another model year, any word that is neither the car's own nor a search's ("/new-vehicles/2027-honda-civic-near-me/", "-specials", a town's name). On a list, such an address without a VIN is a car only when it has the shape of this lot's car addresses (a card's "More like this" search, `/used-vehicles/2016-honda-civic/`, is none; on a lot whose car addresses carry their VIN, no VIN-less one is). At post time `getDetails` is told the car pages the last scan kept (`options.carPages`), so it knows the lot's other cars' addresses as a scan does. The page's first heading counts as the page's own car, so the element around its title and price is never another car's card. On its own page, a car's text is the page without other cars' cards (a "similar vehicles" carousel); for a car read from a list, its own card there, and a car with no card of its own on the list gets no price from the list. A `priceSpecification` typed StrikethroughPrice, ListPrice, MSRP, SRP, InvoicePrice or MinimumAdvertisedPrice, or priced per month or per unit, is never the price. An offer with no `priceCurrency` counts as US dollars only when the page shows that exact amount with a dollar sign. A price range, another currency and kilometres are left out with a reason (`readingNotes`). It has no probe or search of its own; `schemaOrg.js` is the adapter built on it. It names no platform: which platforms publish usable markup is known only once a real site has been scanned. Fixtures: `test/fixtures/structured/` (synthetic; see its `_about.md`).
